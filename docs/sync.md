# Tie 同步逻辑

用户日常只感知 **保存**。同步是保存之后的系统行为，成功时无感；失败或冲突才轻量提示。

分层见知识库页面「架构分层」。相关格式见 [`page-format.md`](./page-format.md)。导出闭包（按引用带走一撮页面）**不是**同步通道，见 [`page-format.md`](./page-format.md#页面闭包导出--导入tie-export--tie-import)（`tie export` / `tie import`）。

## 进程

保存之后，和后台对齐由客户端上的 **同步进程** 做。本机 MCP 写入成功后也会调用与 `tie sync` 相同的同步核心，尽力对齐一次；MCP 协议本身不承担对齐逻辑，后台不会在自己的数据目录里再起同步进程。

| 进程 | 怎么起 | 做什么 |
|------|--------|--------|
| 同步进程 | 在持有本地工作区的机器上：先 `tie sync login` 或 `tie sync register`（桌面端登录会写同一份会话），再 `tie sync --backend-url http://主机:8787 --backend-workspace <该用户的工作区 id>`。`--watch` 按间隔反复对齐 | 把本地页面树和当前登录用户在这一台后台上的工作区对齐。只一边改过就推或拉；两边都改过则记冲突，不覆盖 |
| 后台进程 | `npm run backend:start`（`backend/src/server.js`） | 多租户 API，是同步的对端，也是 HTTP MCP 的宿主。它不在自己的数据目录里再起同步 |

`.tie/sync.json` 只记 `engine: backend`、后台地址和工作区 id。登录会话在应用数据目录的 `backend-session.json`（桌面登录 / 退出，或 `tie sync login` / `tie sync register` / `tie sync --logout`）。同步前向后台确认当前用户，工作区不属于这个用户就拒绝。未登录不能同步。令牌和密码不写入工作区，也不写入页面。

## 连接状态

用户只看到两种状态：

| 状态 | 含义 |
|------|------|
| **本地** | 工作区。可以绑定多个本地文件夹（含 SMB 挂载目录）。页面写在这些工作区里。 |
| **本地 + 服务器** | 在本地之上只绑定一台服务器。绑定并登录后，由同步进程对齐该用户在这台服务器上的工作区。 |

- 服务器同时只绑定一台。解除绑定后回到本地。
- **独立直连 S3 已废弃**（不再提供添加入口；存量只读兼容）。S3 只是服务器的存储能力。

## 保存 vs 同步

| 动作 | 行为 |
|------|------|
| **保存** | 写入当前本地工作副本。落盘成功即保存成功。 |
| **同步** | 已登录并写好 `.tie/sync.json` 时，同步进程再对齐后台。未登录或未配置则不能对齐。 |

流水线（对用户折叠为一次保存）：

1. 写入本地工作副本
2. 若已登录并配置了后台工作区 → 同步进程对齐
3. ② 成功 → 界面仍只显示「已保存」
4. ② 失败 → **仍算已保存**；轻量提示「尚未同步到其他设备」，可稍后重试

同步进程会双向补齐页面附件；正文没有变化时也会检查缺失的附件。文件登记的 `link` 只同步元数据，不上传外部原文件；`copy` 的单文件副本按元数据更新时间同步内容，替换副本后会重传。

后台目前不支持复制目录。工作区含目录副本时，同步会明确报告「目录副本尚未同步」，本地目录和文件保留；不能将其视为已同步完成。单个附件或文件副本仍受后台 20 MB 上传限制。

回收站页面的永久删除会在下次同步时传到后台：仅处理本机已跟踪、后台仍是同一删除版本的页面；未见过的后台页面、正常页面和已变更版本会下载保留。

## 同步矩阵

| 场景 | 机制 | 何时跑 |
|------|------|--------|
| 本机 ↔ 已登录用户的后台工作区 | **同步进程** `tie sync`（服务端再写磁盘或它托管的 S3） | 保存成功之后；`--watch` 按间隔重复 |
| 本机或 SMB 上的多份副本 | **Git** commit + fetch/rebase/push。这是桌面端上多份本地目录的能力，不是同步进程的对端 | 保存后由桌面端对齐这些副本 |
| 后台磁盘 ↔ 后台 S3 | 仅服务端配置，客户端无感 | 运维切换 |
| 分享 / 迁移子集 | **export 闭包** | 用户显式导出，不建立持续同步 |

## Git 运行时（仅本地 / SMB 副本）

- **安装包不自带 Git。**
- 解析顺序：`TIE_GIT` → 应用数据目录已下载的运行时 → 系统 `PATH` 中的 `git`。
- 需要这种本地副本对齐又找不到 Git 时：提示下载同步组件（Windows 可拉取 MinGit 到应用数据目录）。
- Android 不跑 Git。

## 冲突

| 通道 | 策略 |
|------|------|
| 同步进程（后台） | 只一边改过就推或拉。两边都改过，或没有游标且内容不同，记冲突，不覆盖 |
| Git（本地副本） | `pull --rebase`；冲突则中止变基，保留本地提交；用户侧文案避免 rebase 这个词 |

手动「同步并载入」是排障入口：冲掉离线队列，并从磁盘重新读取。它会重载内存里的页面树，不会主动把内存写回文件。

## 与 MCP / Agent

- MCP / `tie` CLI 读写的是某一份工作区树。写入等价于一次保存。
- 文件登记、打开提示、目录导入/导出在本机 CLI 执行；后台 HTTP 不提供宿主文件访问。已绑定后台的本机 MCP 也会将这些操作留在本机。
- 本机 `tie_write`、`tie_import`、`tie_file_ingest` 成功后尽力同步一次，结果附带 `sync.state`：`synced` 为本轮成功，`pending` 为本地已保存但同步未完成，`skipped` 为未绑定服务器。写入落盘成功与同步完成是两件事；同步失败时保留本地结果，不报告为已同步。后台 HTTP 的 CLI 子进程不反向启动同步。
- 已绑定服务器的本机 `tie mcp` 先检查 `/health`，后台正常时经 HTTP 处理页面数据请求。HTTP 异常时返回故障，**不得自动降级到本地**。
- 降级流程：`tie_connection` 的 `action: "status"` 返回故障和 `confirmationId`；Agent 向用户说明故障及将使用本地副本，取得明确同意后，才可调用 `action: "confirm_local"` 并传入该 `confirmationId`、`confirmed: true`。许可仅适用于当前故障期；HTTP 成功后立即撤销。未绑定服务器的纯本地工作区无需此确认。
- 授权优先使用同一服务器的 `backend-session.json` 登录会话；401 时可刷新一次。没有本地登录会话或没有 Tie 应用时，用户主动提供该服务器签发的 MCP token。它只授权令牌绑定的工作区，不替代同步进程的账号登录。
- 无本地应用的原生 HTTP Agent 可使用 `/health` 给出的 `mcp.url`，以 `Authorization: Bearer <MCP token>` 连接。CLI 桥接可通过 `TIE_MCP_URL`（服务器根地址或 `/mcp`）与 `TIE_MCP_TOKEN` / `TIE_MCP_TOKEN_FILE` 连接，此模式无需本地工作区。凭据用客户端凭据管理或私有 token 文件保存，禁止写入页面或提交仓库。

## 已经否掉、不要再接回来的做法

- 用 MCP token 代替同步进程的账号登录
- 同步进程去推 Git 远程
- 本机再启一个 HTTP MCP，或用 `node` 跑 `packages/tie-mcp`
- 客户端直连 S3 作为新增源
- 按页把内容扇出到多份「备份镜像」

## 相关能力

- **导出闭包**：`tie export` / MCP `tie_export` / 编辑器「⇪」— 见 `page-format.md`
- **整树携带**：`.tie` 解决方案 + 目录树；可选 `.tiez`（`tie pack` / `tie unpack`）
- **后台 MCP HTTP**：管理员在「服务」里打开。请求由后台转给 Rust `tie-cli mcp`；MCP token 使用其绑定工作区，登录会话还须指定本人工作区。没绑后台的本机 Agent 直接使用本地 `tie mcp`
- **只读 Web**：浏览器打开 `#/read/<pageId>`
- **Agent 变更**：`.tie/audit/events.jsonl`；右侧栏「变更」
